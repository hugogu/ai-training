# FTN 1.0 改进说明

**对照对象：**用户原始 Financial Transaction Notions 图例和本次可见示例。**日期：2026-10-17。**这是一份独立的设计变更说明；规范正文不依赖这份说明才能读懂。

## 1. 保留的设计骨架

保留圆形账户和方向箭头，保留水平时间轴、Split/Gather、多场景并列及黄色便笺。钱包浅绿、中间账户灰、外部银行账户浅蓝的色彩延续原设计的轻量风格。复杂度只在出现相应业务问题时引入。

最大的变化是让图形外观与业务含义形成稳定对应：账户形状不会因为当前状态改变；箭头线型不会因为“还没成功”而变成另一种事件；一个外框不会同时兼任机构、显示边界和原子事务。

## 2. 原设计与新规范的对应

| 原设计中的理解成本 | 新规范的处理 | 实际改善 |
| --- | --- | --- |
| Wallet、Bank、MP、Rev 均可能以圆出现 | P 表主体；A 表账户；明确 owner/custodian/ledger/purpose | 能回答“谁的哪个账户”，避免把银行收到请求读成银行账户到账 |
| 虚线表示 pending，也用于注释 | L/F/M 线型固定；状态独立；注释无箭头 | 即使黑白打印也能区分消息、账务和资金 |
| “一条交易”可能指客户订单或记账腿 | O、B、leg、effect_ref 分层 | 一次客户扣款可展开为多腿，条数不再暗示多次扣款 |
| Split/Gather 侧重分配形状 | 增加源/目标基数、同域约束和 atomic | 能识别一次提交与跨机构部分成功 |
| 超时与失败边界未明确 | knowledge 与 execution state 分开 | unknown 时查询原请求，不直接生成第二次付款 |
| 历史不可撤销的适用范围较宽 | 已入账事实不可覆盖；取消、冲正、退款新增记录 | 能取消未执行意图，同时保留审计轨迹 |
| 退款靠反向箭头理解 | reverses / returns / refunds / retry_of 明确区分 | 不再把银行退回、客户退款和本地更正混为一事 |

## 3. 金额与完成条件的改善

| 原设计中的理解成本 | 新规范的处理 | 实际改善 |
| --- | --- | --- |
| 正负金额和方向同时传义 | 资金腿用正金额，增减号只用于 Δq | 避免“负金额反向箭头”被重复取反 |
| Lock Target=100 但净到账 99.01 | source_total / source_principal / target_gross / target_net | 能明确产品到底承诺哪一个金额 |
| 1% 费用的计费基数需要猜 | 明确按毛额或净本金计费及舍入 | 区分到账 99 与 99.01，算术和产品含义一致 |
| Base 与 Source、Quote 与 Target 放在一起 | 拆分报价方向与本笔资金方向 | 兑换方向反转时仍能准确阅读 |
| FX P&L 容易成为平衡差额 | 分别记录回收、退款义务、补足及估值口径 | 5 USD 资金缺口不被无依据地命名为整笔总损益 |
| 收到响应、记账成功、受益人到账未统一 | 用 required_legs 与 confirmation_basis 定义完成 | 团队知道“成功”的证据与范围 |
| 零金额分支保留在执行路径 | 改为 no_effect 注释 | 不把没有资金效果的路径当成需要执行的交易 |

## 4. 形式化带来的变化

新增类型化模型 D、正整数最小单位金额、逐域逐币种的余额变动定义，以及 R01-R14 静态约束。机器样例覆盖付款、未知结果、替代执行和平台分费，校验器检查引用、类型、金额、原子批次、证据门槛及重复执行单元等错误。

这使“图看起来合理”与“模型通过明确规则”可以分别评审。验证通过仍不能证明银行真的到账、余额充足、账务分录正确、通道重试安全或退款政策合法；这些属于真实系统和 Domain 配置的责任。

SVG 与 PDF 共用同一组矢量绘图描述，避免两份图例分别维护后发生线型差异。规范 Markdown 是文字源；SVG 是可编辑图形源；PDF 用于审阅与分享。核心 JSON 与示意图不声称自动一一生成。

## 5. 新增复杂度与取舍

**读图成本增加：**需要先理解 L/F/M，以及 O/B 的区别。采用固定页眉和小图例，并允许简单场景仅使用必需符号，控制学习成本。

**证据负担增加：**已确认结果必须带来源引用，未知结果不能隐藏。这会让图暴露更多未决事项，但能减少过早宣布完成的歧义。

**画图约束增加：**一个账户只画一个币种；跨域不能强画成本地原子事务；FX 必须拆腿。这会增加节点，但能避免用一条线隐藏币种、归属和中间义务。

**刻意保留的边界：**没有设计一整套复式总账语言，也没有统一所有银行的状态码、重试协议和最终性规则；没有把本地记账与真实银行头寸自动等同。

## 6. 本次交付与后续验证

已交付规范正文、独立改进说明、两份阅读版 PDF、九幅可编辑 SVG、核心 JSON Schema、四个样例，以及静态校验器和测试。原始 `.graffle` 文档不覆盖修改。

仍应通过真实业务共同验证：

1. 让产品、研发、财务分别阅读付款、未知结果、部分退回三个场景，比较他们对金额、状态及下一步动作的理解。
2. 选一个真实通道，将其查询状态、幂等协议与未执行证据映射到 F/M，确认重试门槛可落实。
3. 用真实账户模型确认 normalized 转移余额与正式总账分录的映射。
4. 将真实费用、FX、退款上限和中间账户收尾规则加入 Domain 配置后，再考虑自动生成图或原生 OmniGraffle 模板。

**建议采用方式：**先将 FTN 1.0 作为团队试用规范。优先观察是否能减少不同岗位对“成功”“到账”“退款”和“同一笔交易”的理解差异，再决定是否扩充符号。
