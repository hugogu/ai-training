# LLM 代码风格微调：SFT + LoRA

建议先读 [前置知识：从基础概念到本练习](前置知识.md)，再运行 Notebook。文档包含关键模型原理、数据形状、代码对应关系与自测解答。

打开 [LLM_LoRA微调.ipynb](LLM_LoRA微调.ipynb)，按顺序执行。这个例子接在 ResNet18 微调之后：仍然是带标签训练、验证与保存，但输入变成 token，监督目标变成期望答案，更新对象变成 LoRA 适配器。

## 为什么选代码风格

对你的学习目标，代码风格比“中国法律知识与逻辑”更适合作为第一个 LLM 微调实验：可以明确给出期望答案，查看参数更新，并直接比较同一需求的前后输出。

法律场景需要区分最新事实、权威出处和论证方式。查找当前条文、版本和依据适合检索；训练论证方式则需要经审核的案例和独立评估。把法条作为原始文本继续训练，不能自动证明模型已经掌握适用规则。对模型是否原本“不熟悉中国法律”的判断，也需要先测基线。

| 希望改善什么 | 合适的办法 |
|---|---|
| 稳定的回答形式、简洁程度、常见代码取向 | 需求/优质答案对做 SFT |
| 精确缩进、引号等确定性规范 | formatter/linter 配置 |
| 当前项目文件、接口及变动 | 检索或提供当前上下文 |
| 复杂设计模式与取舍 | 包含约束、已审核方案和评审修正的丰富样例，配合评估 |

微调可以减少重复的风格指令；具体任务、动态代码上下文和约束仍然需要输入。LLM 的倾向不能替代测试或确定性规范。

## 这个例子实际做什么

- 基础模型：公开的 `Qwen/Qwen2.5-Coder-0.5B-Instruct`，约 0.49B 参数。
- 固定 revision：`ea3f2471cf1b1f0db85067f1ef93848e38e88c25`。
- 材料：当前课程的 pandas/NumPy 操作与项目的简洁、自解释、使用已有库等约定，整理成 32 条人工编写/改写的教学样例。
- 划分：24 条训练、4 条验证、4 条测试；每个逻辑任务只在一个集合中。
- 目标：更倾向输出简洁函数、避免多余说明和显式循环。
- 方法：SFT 只计算 assistant 答案与结束 token 的损失；LoRA 只训练 q_proj/v_proj 的低秩增量，原有权重冻结。

`style_examples.jsonl` 的 `source_refs` 指向相应课程操作的概念参考，`provenance` 标明教学改写。它不是自动扫描你全部项目所得的个人风格数据集，也不是所有答案都来自你的原始实现。不要把 32 条样例的结果解释为模型已经理解你所有设计模式。

模型、训练和输出比较均在本机进行，默认不上传样例。基础模型已经有编程能力；这里观察的是对一组习惯的适应。

## 运行

推荐原生 arm64 Python 3.12。在本目录执行：

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

在 Notebook 内核选择器中选择本目录 `.venv`。先看第一个单元格的版本和设备输出。默认 MPS 可用则使用 MPS，否则 CPU；CPU 可以运行，速度会更慢。本例使用 FP32 LoRA，在当前 CPU/MPS 环境中展示完整流程。

首次从 Hugging Face 下载约 1 GB 权重，存放在 `.cache/`。下载模型需要能访问 Hugging Face；网络失败时先解决该下载阶段，再执行训练，不能把下载等待当作模型训练耗时。后续复用固定版本缓存。

默认 batch size=2、4 个 epoch、最大训练长度 256、LoRA rank=8、学习率 0.0005。长度不足会明确报错，不会默默截断答案。两个版本生成时均使用 512 个新 token 的上限，并单独记录是否触及上限。训练参数是教学起点；不同模型、数据量与设备需要重新评估。

## 按顺序观察

1. 看一条需求/答案对，确认期望代码是你认可的。
2. 查看 tokenizer 和 labels：需求与 padding 标为 -100，答案和真正的 EOS 参与训练。
3. 查看可训练参数比例，确认原有权重冻结。
4. 训练并按验证集答案 token NLL 选择 epoch。
5. 选择完成后，对四条保留测试需求关闭/启用适配器，使用相同 prompt、聊天模板和贪心生成设置。
6. 查看逐条输出、静态风格计数和是否触及长度上限；随后保存适配器并离线重载。

生成时没有附加“按我的风格回答”的系统消息，也没有提供训练示例。模型自带聊天模板仍然存在；测试需求中的函数名、功能和 pd/np 已导入的背景都是任务输入。

## 如何看待评估

答案 token NLL 越低，表示模型对参考答案的概率更高；它不是代码正确率。静态检查统计原始答案是否能解析为 Python、是否仅含指定函数、有无显式循环和冗余 docstring、函数体是否简短。

检查会将 Markdown 包装与代码块结构分开，所以基础模型仅多写了代码围栏时，也能看到其代码结构可能本来就符合要求。这些检查不执行模型代码，不能证明生成函数的语义正确，更不能衡量大型软件架构质量。生成达到长度上限的情况也会单独记录。

`test_lesson.py` 检查 SFT 掩码、EOS/PAD 边界、划分与样例答案，并对几条经过编写和审查的标准答案做功能测试；它不自动执行模型生成代码。运行：

```bash
.venv/bin/python -m unittest -v
```

Notebook 还检查原有权重未变、LoRA 参数已更新，以及适配器离线重载后的 tokenizer、logits 和一次生成是否一致。最终模型如果验证表现没有改善，可以保留第 0 轮的基础状态。

## 一次实际运行与失败案例

在 arm64 Mac 的 MPS、Python 3.12.14、PyTorch 2.10.0、Transformers 4.57.6、PEFT 0.18.1 环境完整运行。LoRA 可训练参数为 540,672，占约 0.1093%；保存的 LoRA 权重约 2.07 MiB，不包含基础模型和 tokenizer。

| 指标 | 基础模型 | 微调后 |
|---|---:|---:|
| 验证集答案 token NLL | 1.4849 | 0.1356 |
| 测试集答案 token NLL | 1.2916 | 0.4780 |
| 原始答案可直接解析为 Python | 0/4 | 4/4 |
| 提取代码块后可解析 | 3/4 | 4/4 |
| 触及统一的 512 token 生成上限 | 1/4 | 0/4 |

第 3 轮验证损失最低；第 4 轮训练损失继续下降，验证损失却回升，因此没有采用最后一轮。原有权重、适配器更新与离线重载检查均通过。

模型缓存就绪后，还完成了整本 Notebook 的离线运行：本次约 68 秒，其中参数训练与逐轮验证约 9 秒，其余主要是加载和逐 token 生成。运行时间随设备变化。

风格变化清楚，但本次输出仍有语义错误：

- `remove_blank_text` 只删除缺失值，没有删除空串和纯空白文本。
- `get_top_indices` 取了最大的 k 项，却忘记反转成要求的降序。

这两个函数都通过了静态风格检查。它们说明“答案简洁且能解析”与“满足全部需求”需要分别评估。本例保留原始结果，未根据这些测试输出修改训练数据或训练超参数。四条相近领域的小测试也不能证明模型已掌握个人设计模式。

## 保存与扩展

`outputs/adapter/` 保存 LoRA 参数、配置、tokenizer 与聊天模板。它不是一个独立完整的基础模型；部署时需匹配同一基础模型 revision。`outputs/manifest.json` 记录模型、样例哈希和超参数，`outputs/report.json` 保留前后输出与度量，`outputs/learning_curve.png` 保存曲线。

如果要进一步学习你真实项目的偏好，收集“需求及必要上下文 → 已认可实现”或“评审意见 → 修正实现”。清理过时、临时、生成和未认可的代码，按函数、文件、PR 或时间分组划分，防止改名副本跨训练与测试。对复杂设计模式，还要加入约束、取舍与反例，并用功能测试和人工评审检查是否产生能力退化。
