# 从语言模型基础到 SFT 与 LoRA 代码风格微调

适合知道监督学习、训练/验证/测试和损失函数，但尚不熟悉大语言模型的读者。先读本文，再进入 [LLM_LoRA微调.ipynb](LLM_LoRA微调.ipynb)；环境安装见 [README](README.md)。图像训练循环不熟悉时，可先看 [ResNet18 前置知识](../图像分类微调/前置知识.md)第 7 节。

本练习的目标是让已有代码模型更偏好一组回答习惯。训练材料是 32 条人工整理的教学样例，不代表已经提取或学会一个人的完整代码风格。

## 1. 从图像分类切换到文本生成

两类任务都通过参数把输入映射为数值得分，但预测单位不同：

| 项目 | 图像分类 | 本练习的语言模型 |
|---|---|---|
| 输入 | 图片张量 | token 编号序列 |
| 预测目标 | 每张图一个类别 | 每个位置的下一个 token |
| 输出形状 | `[N,类别数]` | `[N,序列长度,词表大小]` |
| 标签 | 类别编号 | 参考答案中各位置的 token 编号 |
| 推理过程 | 一次前向得到分类得分 | 逐个生成 token，直到结束或达到上限 |

LLM 是 Large Language Model，大语言模型。它可以生成代码，是因为预训练及后续训练使参数捕捉到文本和代码的规律；它并非在内部自动执行每段代码后再输出。

## 2. token、词表、embedding 分别是什么

Tokenizer 把字符串拆成 token，再映射到词表中的整数编号。一个 token 可能是完整单词、子词、字符片段或特殊标记；**不要假设一个汉字、一个单词或一个 Python 变量固定等于一个 token**。

例如，`return data.sum()` 会被分成某个 token 序列。具体拆法和编号由所用 tokenizer 决定，不应凭文字长度猜测。可以用练习已经加载的 tokenizer 观察：

```python
# 在 Notebook 加载 tokenizer 后执行，查看当前模型实际怎样拆词。
text = "return data.sum()"
ids = tokenizer.encode(text, add_special_tokens=False)
print(ids)
print(tokenizer.convert_ids_to_tokens(ids))
print(tokenizer.decode(ids))
```

Embedding 是一个可学习的查表矩阵，把每个编号变成向量。编号之间的数字距离通常没有语义意义；编号 100 不意味着比编号 50 “大一倍的意义”。向量经过后续网络处理才成为包含上下文的表示。

词表和类别标签表有相似之处：编号必须按正确映射解释。但语言模型不是从“整句答案清单”选一项，而是不断从词表选择下一个 token，组合成此前未完整出现过的句子和代码。

## 3. Transformer 怎样利用上下文

### 3.1 一条足够读懂练习的结构链

```text
字符串 → tokenizer → token 编号 → embedding 与位置信息
      → 多层 Transformer → 每个位置的词表 logits
      → 选下一个 token → 追加到序列 → 继续生成
```

本例 Qwen2.5-Coder-0.5B-Instruct 是面向代码的、decoder-only 自回归 Transformer。`0.5B` 表示大约五亿参数这个量级，`Instruct` 表示已经做过面向指令对话的训练；不是从随机权重开始。具体模型信息以 [Qwen 模型卡](https://huggingface.co/Qwen/Qwen2.5-Coder-0.5B-Instruct)为准。

### 3.2 注意力中的 Q、K、V

每层为当前位置计算 Query（查询），为可见位置计算 Key（键）和 Value（值）。Query 与 Key 的匹配决定应该从哪些位置汇总多少 Value 信息。

单个注意力头可简化表示为：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}+M\right)V
$$

$d_k$ 是键向量维数，$M$ 表示遮罩：不允许看到的位置会被屏蔽。多头注意力让不同子空间分别计算这类关系，再组合结果。Transformer 还包含前馈网络、归一化、残差连接和位置信息；不能把它只理解成一次 softmax。

代码中的 `q_proj`、`v_proj` 是生成 Query、Value 的线性投影模块名。本例在这些模块上加 LoRA；它们不是训练集的提问文本和答案文本两个字段。

### 3.3 因果遮罩与生成

自回归模型在预测下一个 token 时，只能使用当前及更早的输入位置。训练时可以把整段答案一次送入，并行计算各位置的预测损失；因果遮罩防止某个位置偷看后面的答案。

推理时答案尚不存在，只能先生成一个，再把它作为后续上下文，逐步继续。KV cache 缓存已有位置的键和值，减少重复计算；它不等同于把新知识永久写入模型参数。本例训练关闭生成缓存，生成时显式开启缓存。

## 4. 从 logits 到一个回答

每个位置的输出是一组词表 logits。softmax 可以将它们转换成该位置的 token 概率分布，然后按生成策略选一个 token。

- 贪心生成：选择当前最高分的 token；本例用 `do_sample=False` 进行前后比较。
- 采样生成：根据概率抽样，可用 temperature 等参数调整分布。
- EOS：回答结束标记。
- `max_new_tokens`：新生成 token 的上限，达到上限不代表代码已经完整。

本例的 `MAX_LENGTH=256` 控制训练样例的总长度，包括提示词、答案和必要标记；`MAX_NEW_TOKENS=512` 是生成阶段的新回答预算。二者是不同阶段的设置，不能用它们判断基础模型理论支持的上下文上限。

`generate()` 对本例模型返回的序列包含原始提示词，因而用：

```python
# output_ids 形状为 [批次, 提示词长度 + 新回答长度]。
answer_ids = output_ids[0, input_ids.shape[1]:]
```

`[0]` 取批次中第一条，切片排除原有提示词。返回结构和生成细节可查 [Transformers 文本生成说明](https://huggingface.co/docs/transformers/llm_tutorial)。

## 5. 为什么还要聊天模板

模型接收 token，不直接接收 Python 的 `{'role':'user'}` 字典。聊天模板把 user/assistant、内容及边界标记编码成模型训练时使用的格式。

即使本例不额外放“请按我的风格回答”这样的系统指令，也仍需要聊天模板。它负责区分谁说话、从哪里开始回答，并不是额外检索出来的知识。使用不同模板可能让同一段文字产生不同 token 输入。

## 6. 预训练、SFT、LoRA、RAG 如何区分

| 名称 | 解决的主要问题 | 是否改变参数 |
|---|---|---|
| 预训练 | 从大量文本学习基础分布和表示 | 是 |
| 继续预训练 | 继续适应某种领域文本 | 是 |
| SFT：Supervised Fine-Tuning | 根据需求学习审核过的期望回答 | 是 |
| LoRA：Low-Rank Adaptation | 用少量附加参数完成适配 | 更新增量参数 |
| 提示词 / few-shot | 在当前上下文交代要求或示例 | 否 |
| RAG：Retrieval-Augmented Generation | 先检索资料，再作为上下文生成 | 通常推理流程本身不改参数 |

SFT 是训练目标和材料组织方式，LoRA 是参数更新方式，所以二者可以组合。法律原文、原始代码文件，与“需求及必要上下文 → 认可的回答”不是同一种监督材料。

对代码风格，稳定的回答取向适合尝试微调；当前接口、最新文件仍适合提供上下文或检索；引号、空格等确定性格式适合 formatter。训练不能替代这些边界。

## 7. 一条监督样例如何形成损失

本例将需求、答案及 EOS 拼在一个输入序列中，但只对答案部分计算损失。以下编号纯为示意，不是真实 tokenizer 编码：

```text
位置             0     1     2     3     4     5
内容             需求  边界  答1   答2   EOS   PAD
input_ids        11    12    21    22    99    99
attention_mask    1     1     1     1     1     0
labels          -100  -100   21    22    99   -100
```

- `input_ids`：模型实际读取什么。
- `attention_mask`：哪些位置是真实输入，哪些只是补齐。
- `labels`：哪些位置提供训练目标；`-100` 在这里表示忽略该位置的损失，不是词表里的 token。
- EOS 与 PAD 即使编号相同，也按**位置**区分：真正结束需要学习，批次补齐不需要学习。

计算下一 token 损失时，模型内部将前一个位置的预测与后一个位置的标签配对。示例中位置 1 的预测要学习输出位置 2 的“答1”；不需要在外部再次手工移动 labels。

训练期间输入中包含参考答案，这是 teacher forcing。它让模型在真实前缀条件下学习下一 token，不代表推理时已经知道答案。

设参与监督的 token 位置集合为 $S$，平均负对数似然为：

$$
L=-\frac{1}{|S|}\sum_{t\in S}\log p_\theta(y_t\mid y_{<t},\text{需求})
$$

模型给参考答案的概率越高，损失越低；换一种同样正确但措辞不同的答案，参考答案损失也可能不同，因此 NLL 不是功能正确率。关于答案掩码可查 [SFT 文档](https://huggingface.co/docs/trl/sft_trainer)；本例自己实现了编码和训练循环，没有使用该文档中的 Trainer API。

## 8. LoRA 为什么能少训练很多参数

对于一个线性层，原权重 $W_0$ 的形状为 $d_{out}\times d_{in}$。LoRA 冻结它，另学两个较小矩阵：

$$
W_{effective}=W_0+\frac{\alpha}{r}BA
$$

其中 $A$ 为 $r\times d_{in}$，$B$ 为 $d_{out}\times r$，$r$ 是低秩维度。数学简化下，增量需要 $r(d_{in}+d_{out})$ 个参数，而完整矩阵有 $d_{in}d_{out}$ 个。

例如输入输出维数都为 1024、rank=8，增量矩阵共 16,384 个参数，完整权重有 1,048,576 个。这只是说明数量关系，不是声称本例每层恰好是此尺寸。

rank 越大通常允许更丰富的增量，也增加参数与开销，并不保证效果越好。本例只在 q_proj/v_proj 使用 rank=8，其他模块保持冻结。LoRA 也没有使基础模型文件消失：运行仍需要基础权重、激活等内存。配置含义见 [PEFT LoRA 文档](https://huggingface.co/docs/peft/developer_guides/lora)。

本例是 FP32 LoRA，**没有**把基础模型量化到 4 位；QLoRA 是另外一种结合量化基础模型与适配器训练的方案，可接着看 [量化前置知识](../模型量化/前置知识.md)。

## 9. 数据、训练、评估的边界

本例将逻辑任务划分为 24/4/4 条训练、验证和测试样例。改函数名后的相同任务不能分别放进训练和测试来声称泛化；真实项目还需按文件、PR、任务族或时间隔离近似样例。

训练仍是 `zero_grad → forward/loss → backward → step`。梯度裁剪降低过大梯度带来的更新风险；验证损失选择保存哪轮，测试只在选择完成后比较。若训练样例很少，训练损失下降可能主要反映记忆，不能推断复杂设计能力提升。

| 评估 | 可以说明什么 | 不能直接说明什么 |
|---|---|---|
| 参考答案 NLL | 对这些参考答案的偏好 | 生成代码必然正确 |
| 语法、函数数量等静态检查 | 输出形式是否匹配 | 边界条件和算法是否正确 |
| 功能测试 | 在所覆盖输入上的行为 | 所有场景正确或架构合理 |
| 人工评审 | 需求、取舍与可维护性 | 无需独立样本或执行检查 |

真实结果中有“删除了缺失值却没删空白字符串”的输出：风格检查通过，功能仍错。测试只有 4 条也很不稳定，不能当作稳定的个人风格能力证明。

## 10. 为什么保存的是适配器

LoRA 保存的是增量及其配置。完整恢复需要：

```text
同一基础模型与 revision + LoRA 适配器 + tokenizer/聊天模板 + 生成配置
```

tokenizer 的词表顺序或基础权重版本不匹配，适配器就可能无法正确工作。本例保存数据哈希和版本清单，离线重载后比较编码、logits 和一次生成结果。

`save_embedding_layers=False` 对本例成立，因为没有扩充词表或训练 embedding；不能把这个设置不加判断地复制到改变过词表的任务。合并适配器与基础权重属于另外的导出操作，保存一个小适配器并不等于完整模型只占几 MiB。

## 12. 自测与参考解释

1. **为什么一个回答有许多组 logits？** 每个 token 位置都预测下一个 token，输出同时包含批次、位置和词表三个轴。
2. **需求不算损失，模型还能用到它吗？** 能，它仍在 input_ids 中；忽略的是这些位置作为预测目标的损失。
3. **SFT 和 LoRA 只能二选一吗？** 不能这样分类；前者定义监督方式，后者定义参数更新方式，本例同时使用。
4. **适配器很小，训练显存就同样小吗？** 不会，基础权重、中间激活和其他状态仍占内存。
5. **能输出简洁代码是否表示学会设计原则？** 不表示，必须用新任务的功能与设计评估判断，不能用形式检查替代。
